## 2. Supplied code, executed as received

Executed on PostgreSQL 16.15 in a disposable cluster before any change:

* `0001_foundation.sql` applied without error.
* `verify_isolation.sql` printed "Isolation checks passed; fixture changes rolled back."
* The eight Python unit tests passed.

Targeted probes then showed four problems the supplied checks did not cover:

| Probe | Observed | Consequence |
|---|---|---|
| Apply the migration to a second database in the same cluster | `ERROR: role "axiom_runtime" already exists` | Roles are cluster-global; creating them inside a per-database migration breaks upgrades, shared clusters and test databases |
| `set_config('axiom.tenant_id', ..., false)` then a new transaction on the same connection | Tenant rows still visible in the next transaction | A single misuse of session scope leaks one tenant's context through a pooled connection |
| Runtime inserts a case with `workflow='closed'` | Accepted | Domain commands can be bypassed at creation |
| Runtime attempts any case transition | `permission denied for table finding_cases` | No path existed for legitimate state changes, so the tested state machine could not be used |

## 3. Code review findings

* `ClosureEvidence` is a bag of booleans (`verification_passed`, `deployment_matches`, ...). The docstring says it must
  be loaded from trusted records, but nothing enforced that, and the type invites passing client flags. Replaced by
  service commands that load verification runs, remediation reports, risk acceptances and evidence rows themselves.
* Only the closure guard existed. The other transition guards in the specification table (scheduled investigation,
  recorded assessment with limitations, authorised remediation decision with assigned owner, approved or recorded
  external work, deployment-identified change, verification outcomes) were absent.
* `require_permission` checks exact scope only (documented), has no role concept, and compares a timezone-aware `now`
  against possibly naive grant timestamps.
* `case_events` had no link to an audit record and `outbox` could only reference case events, so neither B12
  (audit atomic with change) nor generic event publication was expressible.
* `evidence_objects` lacked the `uploaded` and `rejected` states and had no rule that only verified evidence may
  support decisions.
* No migration ledger, no checksum protection, no separation of owner and runtime roles beyond one group role.

| # | Finding | Resolution |
|---|---|---|

| R2 | Specification 10 and Data design 7 make asset retirement a distinct closure reason needing lifecycle evidence, but the specification's transition table lists only acceptance, dismissal and duplicates for `review_required -> closed`. | Retirement closes from `review_required` with reason `asset_retired`, verified lifecycle evidence and all affected assets retired (ADR 0004). |
| R3 | Disposition enumeration has no value for retirement. | Closure reason is the authoritative classification; disposition records intended treatment (ADR 0004). |
| R4 | "Deferral remains open with review date" does not say which workflow state. | Deferral keeps `review_required` with `disposition=defer` and a mandatory `review_at` within 365 days. |
| R5 | "Inconclusive assessments cannot close as verified remediated" is ambiguous between the case assessment and the verification result. | Both enforced: verified closure needs `assessment=supported` and a passed, complete verification. |
| R6 | Job execution states (spec 4) differ from action execution states (data design 7). | Treated as different records: workflow jobs versus external action executions. To be reconciled when the action runner is built. |

## 5. Assumptions judged unrealistic or unverifiable here

* **Vendor connector support.** Live validation needs licensed accounts for Tenable, Qualys, Rapid7, Snyk, Burp,
  Defender, Security Hub, Jira, ServiceNow and GitHub. None were supplied. Connectors can reach "fixture-tested"
  with public or synthetic samples; "sandbox-validated" needs accounts.
* **RPO 15 minutes / RTO 4 hours.** Achievable with managed PostgreSQL point-in-time recovery, but only demonstrable
  on a deployment profile with continuous WAL archiving. Not testable in this workspace beyond local restore drills.
* **State-of-the-art claims.** Require a labelled, held-out evaluation set with human reference decisions. No such
  dataset exists yet; building it is tracked as EVAL-01..EVAL-05.
* **Hostile code execution isolation.** The specification correctly says container boundaries are insufficient; no
  sandbox technology has been selected, so any capability that runs untrusted code stays disabled.

## 6. Missing controls identified (now tracked)

Idempotency-key storage for external-effect commands (API-07), per-tenant quotas (TEN-10), export controls
(RPT-06), cache isolation (TEN-07; no cache exists yet), legal holds and deletion jobs (EVD-07, A20), audit read
segregation for installation operators (OPS-05), signed audit checkpoints (EVD-08), and webhook signature and replay
protection (ING-08).
